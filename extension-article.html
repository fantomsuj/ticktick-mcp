A Chrome extension, not another dashboard

The Browser's Conscience

The best TickTick upgrade would not replace the web app. It would sit quietly inside it, making every task a little more honest.

By TickTick Companion
An editorial product brief for turning the triage dashboard into native-feeling browser intelligence.

The mistake would be to convert TickTick Companion into a smaller dashboard that floats beside TickTick. TickTick already has a polished web app, and it already owns the broad task-management canvas: capture, lists, calendar, Kanban, filters, reminders, Pomodoro, habits, collaboration, and statistics. The extension should leave those alone.

What TickTick does not quite provide is judgment at the moment of contact. In the real first screen, All opens onto a large Overdue group and an empty detail pane. TickTick can show that backlog. It does not tell you which overdue item deserves recovery, which should become a day anchor, and which should be parked without drama.

The product is not a planner. It is a layer of conscience on top of one.

The Native Feature That TickTick Does Not Have

The companion should become an inline decision layer. Its best features are not new screens. They are small interventions inside existing surfaces: one recommended move on an overdue row, a five-task guardrail in the All header, a pressure mark beside a project, a short explanation in the task detail pane.

The current dashboard already has the ingredients: overdue scoring, reschedule memory, Waiting detection, Someday routing, Today capacity, project-family pressure, Inbox triage, next-slot scheduling, and End-of-Day rollover. The extension should package those as native-feeling micro-features on the first page you actually see.

The Core Features

1. One Recommended Move

Every visible overdue task should get, at most, one primary recommendation: Keep Anchor, Next Slot, Park, or Follow Up. The explanation can sit beside it as a quiet label. Secondary choices belong in the detail pane or the capacity guard, not sprayed across every row.

2. Today Capacity Guard

Today should usually stop at five real commitments. Day-only tasks, the ones marked for a date but not a time, should be treated as anchors: the most important work for the day. Timed tasks then orbit around those anchors instead of quietly crowding them out.

When a user moves one more task to Today, the extension should check the current day commitment count. If Today is already full, it should ask for an honest trade: protect the anchors, move the new task to the next available slot, displace something else, or move anyway intentionally.

3. Inbox One-Pass Triage

TickTick already lets you edit project, priority, and due date. The extension should reduce the friction of doing all three at once. In the Inbox, a compact triage strip can assign the task, set its priority, choose a date, park it, or drop it.

4. Waiting That Ages

A Mark Waiting action should prefix the task, move it to the configured Waiting home, and keep it visible when it becomes stale. Waiting should not become a hiding place. It should become a follow-up system.

5. Reschedule Memory

The local event log is the secret weapon. A task pushed three times deserves a different kind of label than a task that simply happens to be due tomorrow. The extension can say what TickTick's dates alone cannot: this has become a pattern.

6. Project Pressure

Beside project names in the left sidebar, small bars can reflect pressure from overdue tasks, Today commitments, Waiting count, and total active load. It should feel less like analytics and more like weather.

The Architecture

The extension should be thin. It should not own OAuth secrets, refresh tokens, complex TickTick API behavior, scoring logic, or the event log. Those already live cleanly in TickTick Companion. The Chrome extension should observe the TickTick web app, decorate it, and ask the Companion API to make decisions or perform mutations.

The rule is simple: Chrome owns placement, Companion owns judgment, and TickTick remains the source of truth. The extension reads TickTick's web UI only to identify visible tasks and place native-feeling controls. It never calls TickTick's Open API directly.

Layer 1 Content script Find task rows, detail panes, headers, and sidebar project names.
Layer 2 DOM adapter Map TickTick elements to task IDs, project IDs, and visible state.
Layer 3 MV3 service worker Validate messages, call Companion, and keep only disposable extension state.
Layer 4 Companion JSON API Return decorations, run actions, enforce auth, and reuse dashboard behavior.
Layer 5 TickTick Open API Reached only through the existing Python client, token store, cache, and event log.

This split keeps credentials out of the browser extension, preserves the tested Python logic, and makes the extension resilient. If TickTick changes a selector, the DOM adapter changes. The product brain does not.

The Backend Contract

The extension needs a small JSON surface beside the existing HTMX dashboard routes. The dashboard can keep rendering HTML; the extension needs structured decisions, status, and mutation results.

GET /extension/api/status

Returns Companion readiness, dashboard authentication state, cache freshness, version, supported extension capabilities, and whether TickTick authorization is usable.

POST /extension/api/decorations

Accepts visible task and project identifiers plus the current TickTick surface. Returns one recommendation per task, stale Waiting signals, reschedule memory, capacity state, and project pressure.

POST /extension/api/actions

Executes the same server-side actions as the dashboard: reschedule, next slot, Someday, Waiting, priority, Inbox assignment, complete, delete, and rollover. Returns refreshed decorations after the write.

POST /extension/api/capacity-check

Checks a candidate Today move before mutation. Returns the current commitment count, cap, protected anchors, overflow tasks, and the confirmation choices required to proceed.

POST /extension/api/diagnostics/dom

Records selector health, detected TickTick route, missing identifiers, and extension version. It never mutates tasks and exists to catch TickTick UI changes early.

POST /extension/api/settings

Saves extension-facing preferences such as enabled surfaces, local or hosted Companion origin, Dida365 support, and optional diagnostic reporting. TickTick tokens stay server-side.

The Chrome Rules

The extension should start as Manifest V3. Its service worker is event-driven and disposable, so important state belongs in chrome.storage, not globals. Content scripts should observe and decorate TickTick, then message the service worker. The service worker should validate those messages and call only declared Companion origins.

Narrow permissions

Content scripts should match only TickTick and Dida365 pages. Host permissions should cover only the local Companion server and an optional configured hosted Companion origin.

Untrusted page edge

Every content-script message must be treated as input from a risky boundary. Validate action names, task IDs, project IDs, source URL, and payload shape before forwarding.

No remote code

Companion may return data, recommendations, and labels, but not executable JavaScript or a remote command language. Extension behavior ships in the package.

The Fragile Part

TickTick's DOM is useful, but it is not a public API. The extension should treat selectors as a watched adapter layer, not as invisible plumbing.

One adapter

Keep selectors, route detection, task ID extraction, project ID extraction, and injection anchors in a dedicated DOM adapter module.

SPA-aware observation

Use MutationObserver and route-change detection to refresh decorations when TickTick changes lists, opens detail panes, or rerenders virtualized rows.

Quiet failure

If identifiers cannot be found, remove injected UI, report selector health, and leave TickTick fully usable. A broken adapter should never break the task app.

What Not To Build

  • No side panel.
  • No replacement dashboard.
  • No second calendar.
  • No direct TickTick API calls from the extension.
  • No OAuth tokens or client secrets in Chrome storage.
  • No custom Kanban board.
  • No Eisenhower duplicate.
  • No Pomodoro clone.
  • No habit tracker.
  • No broad capture replacement.

The Build Plan

Phase One: Prove the Thin Slice

Build the MV3 scaffold, DOM adapter, service-worker message broker, status endpoint, decorations endpoint, and one end-to-end inline recommendation that executes through Companion and records the normal event log.

Phase Two: Make Workflows Native

Add Today capacity guard, Inbox one-pass triage, detail-pane actions, stale Waiting annotations, sidebar pressure marks, Dida365 URL support, and selector diagnostics for TickTick SPA changes.

Phase Three: Make Judgment Ambient

Add End-of-Day rollover, weekly review nudges, command-palette actions, extension-specific Puppeteer tests, service-worker restart tests, and optional agent-assisted task breakdowns through the existing bridge.

Success Criteria

  • The extension detects visible task and project IDs on Today, Inbox, project lists, and the task detail pane without broad Chrome permissions.
  • Companion returns the same recommendations the dashboard would derive from the same TickTick snapshot and local event log.
  • At most one inline recommendation renders per task, with no layout shift that makes TickTick harder to use.
  • Every mutation goes through Companion, reuses the existing TickTick client behavior, refreshes affected projects, and records one event log entry.
  • The Today capacity guard blocks accidental overcommit unless the user intentionally confirms the tradeoff.
  • When Companion is offline, TickTick authorization expires, or selectors break, the extension removes its controls and leaves TickTick usable.
  • Extension tests load the unpacked MV3 package, exercise content-script messaging, verify injected recommendations, and survive service-worker restart behavior.

The extension should make TickTick feel less like a database of obligations and more like a system that notices when reality has changed.
